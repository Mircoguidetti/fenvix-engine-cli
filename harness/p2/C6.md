## Tried and reverted

1. The outside-files recorder reading the raw stack (e6b7359f, reverted in ffae5671 + 1a20e23b). `byProjectOutside()`
   formats `String(new Error().stack)` with 40 frames on every fs call made outside a test (every existsSync of module
   resolution at import). Building the same text from the raw call sites (its decision looks only at Node's module
   loader frames and detjs' own) made alakajam 61-63 s -> 43 s at 1 worker, agentsys, yalc and codex-multi-auth
   unchanged. Not identical on alakajam (`data/c6-ident/IDENTITY.txt`):
   - `files_read_outside_tests` 311 -> 149 entries: the 162 gone are reads of project `.ts` files made by
     source-map-support itself while the engine formatted its own stack (`@cspotcode/...` is scoped, so `INFRA` does not
     match it).
   - In 5 tests one `time` event's site moved from `server/core/forms.ts:255` (the `new Date()` line, correct) to
     `:238` (wrong): the site lookup (`resolveFormatted`) mapped that file correctly only after the import-time
     formatting had made source-map-support load its map.
   Its test `node/test/p2-c6-outside-stack.test.js` was deleted with it (new in e6b7359f, never released).
2. A first capture of 10 frames instead of 8 in `sites.resolve()` (7ae4a50a, reverted in a966688c): the same site by
   construction (test `node/test/p2-c6-depth.test.js`, deleted with it), identical results in 3+3 fixed runs, but no
   gain: agentsys median 17.56 -> 17.44 s, alakajam 58.79 -> 60.90 s (ranges overlap).

`hazards()` (C4: 16 s -> 50 ms on codex-multi-auth's markers) and the lane bookkeeping do not apply at 1 worker.

## Open: design question D7 (sent to the coordinator 2026-11-28)

The one large per-file cost found (about 19 s of alakajam's 60 s at 1 worker) can only be removed by changing what the
engine records on repositories like alakajam: (a) leave it; (b) make the site lookup independent of the import-time
warm-up (resolveFormatted loads the file's source map itself, or the recorder formats once per source file), then take
the raw stack, with the founder accepting the changed sites and `files_read_outside_tests` as a proof-field change and
tests that the mapped line is the right one; (c) other.

  CORRECTION (D9, 2026-11-28): an earlier version of this list had 6, counting `codex-bin-wrapper.test.ts` "falls back to
  native resume" from the first identity runs (cf9ac636, one run per engine). That listing's digest differs in every one
  of the 7 runs, old and new (its entries are named after a child's real pid): it varies run to run with both engines,
  not between them. Explained by D9 = B (no engine bug found, no code change):
  - `test/accounts.test.ts` (1 test), 12 -> 16 events: an un-awaited background write (`lib/codex-cli/writer.ts:361`
    through `lib/storage/file-lock.ts`) reads `CODEX_CLI_CONFIG_PATH` (`state.ts:253`), `CODEX_HOME`
    (`runtime-paths.ts:48`), `process.pid` and `crypto.randomUUID` (`file-lock.ts:148`). With the old engine those reads
    come after the test ended (with the old engine, 3 of the `CODEX_CLI_CONFIG_PATH` reads have no test running); with the
    new engine they come before the test ends, so they are its events. The old engine resolved their site correctly
    (`state.ts:253`): the earlier guess (a wrong mapping hid them) was wrong. Timing: the test does not await the write.
  - `test/codex-bin-wrapper.test.ts` "can forward without capturing child stdio" (1 test), 76 -> 84 events: the test's
    cleanup (`rmSync` recursive, line 58) finds `<tmp>/codex-home/multi-auth/status-quota-refresh.lock` in the 8f3f831c
    runs and an empty directory in the a148bca2 and cf9ac636 runs. `scripts/codex.js` 1046-1076 takes that lock for a
    quota refresh it starts as a detached, unref'd child, and removes it only if the launcher outlives the refresh
    (its own comment: otherwise "they will NOT fire", the lock is reclaimed after 10 minutes). Timing: whether the
    refresh has ended when the test removes the directory.
  - `test/quota-cache.test.ts`, `test/refresh-queue.test.ts`, `test/rotation-proxy-state.test.ts` (3 tests): only
    `fs.stat.mtimeMs` / `ctimeMs` values differ. `src/fstime.js` maps a file time onto the virtual clock by its real
    age at the test start or by the last clock event before it; such a value "depends on when the run happens" (its
    header), is a real-clock read for the cache, and `verify` never calls two runs with it identical. Any speed change
    before the read moves it.
So outside `files_read_outside_tests` and the sites, the 5 codex-multi-auth differences come from timing (two races in
the repository's own code, and file times that are real-time reads by design), none in an outcome.
